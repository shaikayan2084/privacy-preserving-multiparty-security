System Architecture

Five-Layer Design

The architecture is modular and compliant with cloud security principles — each layer maintains isolation and minimizes the risk of data leakage across boundaries.

1 — Input Preparation Layer

Data owners encode datasets into cryptographic shares using Shamir's Secret Sharing and local AES-256-GCM encryption. Raw data never leaves the client device.

Shamir SSS
AES-256-GCM
HKDF Key Derivation

2 — Confidential Computation Layer

Cloud nodes execute SMPC protocols over shares. Only encrypted/masked intermediate values are exchanged. No node accesses unencrypted data at any point.

3 — Storage & Communication Layer

TLS 1.3-encrypted messaging between nodes, redundant storage, and authenticated message exchange ensure data integrity and reliability across the distributed system.

4 — Output Aggregation Layer

Partial computation results are combined via threshold-based Lagrange interpolation to reconstruct the final output, delivered securely to authorized parties only.

Security Model

Threat Model & Mitigations

Threat CategorySecurity AssumptionMitigation Strategy
🕵️ Honest-but-Curious CloudCloud nodes follow protocol correctly but may attempt to infer private data from computation patterns.SMPC protocols ensure computations occur over secret shares; no single node holds complete information.
🎯 External Adversary (MITM)Network channels are vulnerable to interception or packet manipulation by external actors.TLS 1.3 encryption and authenticated message exchange maintains data integrity and confidentiality.
🤝 Colluding NodesA limited subset of nodes may collaborate to reconstruct secret data from their combined shares.Threshold-based SMPC tolerates up to k-1 colluding nodes. Detection and isolation policies apply beyond threshold.
💻 Compromised Client DeviceEnd-user devices assumed secure during preprocessing and share generation phase.Client-side validation, secure key storage, and pre-upload AES-256-GCM encryption prevent data leakage.
⚠️ Faulty / Unresponsive NodesSome nodes may fail or behave unpredictably during computation rounds.Fault-tolerant SMPC with redundancy and checkpoint recovery maintains correctness and service continuity.
Application Security

Web Application Security Features

🔒

Rate Limiting

Login: 20/min, 100/hr. Password reset: 5/hr. API endpoints: 30/min. Prevents brute force and DoS attacks.

Flask-Limiter
🚫

Account Lockout

Temporary lock after 5 failed login attempts. Configurable lock duration. Security event logged for each failure.

bcrypt timing-safe
🔑

Password Security

bcrypt with 12 rounds + unique salt per hash. Minimum 8 characters enforced server-side. Timing-safe comparison.

bcrypt rounds=12
📱

MFA / TOTP

Time-based OTP via Google Authenticator / Authy. QR code provisioning. Session-level MFA verification tracking.

pyotp TOTP RFC 6238
🍪

Secure Sessions

HttpOnly cookies prevent XSS theft. SameSite=Lax prevents CSRF. Session tokens rotated on every login.

1-hour expiry
🛡️

CSRF Protection

CSRF tokens on all forms. Token validated server-side on every POST. API calls require X-CSRFToken header.

Flask-WTF
✉️

Email Verification

SHA-256 hashed tokens. 24-hour expiry. Generic responses prevent email enumeration attacks.

Single-use token
🔄

Password Reset

Single-use tokens with 30-minute expiry. Invalidates all sessions after reset. Generic "if email exists" response.

No email enumeration
👑

RBAC Authorization

Role-based access control with admin/user roles. Server-side enforcement — frontend-only checks never relied upon.

Admin · User roles
📊

Security Logging

All login attempts logged with IP, user agent, timestamp, and failure reason. Admin can review security events in real-time.

Structured event logs
🧩

SQL Injection Prevention

SQLAlchemy ORM with parameterized queries. Input validated server-side on all endpoints. No raw SQL strings.

SQLAlchemy ORM
💬

Generic Error Messages

Never reveals whether email or password is wrong. Never exposes internal logic. Consistent timing prevents side-channel leaks.

No enumeration
